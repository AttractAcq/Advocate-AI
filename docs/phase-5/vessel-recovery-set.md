# Coordinated synthetic vessel recovery set

The vessel recovery capture requires a stopped, signed installation. It holds the vessel operation lock and the policy directory lock, verifies that only the labelled Knowledge data volume remains, freezes the approved Core sources, policy, audit chain and SQLite history, then starts the signed Knowledge image on that volume without network access. Managed Core configuration, audit, history and approved source files must each have one filesystem link; a hard-linked outside alias refuses capture. This does not replace process isolation or protected storage. The signed Core image checks the complete document index against the frozen source bytes. A bounded PostgreSQL custom dump and the frozen Core files enter one encrypted restic snapshot. An Ed25519 schema-2 receipt signs the snapshot ID, release and installation IDs, source and passage counts, audit checkpoint, dump hash and a canonical digest of all five Knowledge tables. The digest includes vector values and is checked before and after the dump. Schema-1 receipts remain verifiable for older clean restores, but cannot authorise a new release switch because they lack the row digest.

Restoration first verifies the receipt and encrypted repository, then restores into a new directory. It checks every restored source, policy, audit checkpoint, SQLite integrity and dump hash against the receipt. Clean activation also compares the restored database's Knowledge row digest with schema-2 receipt evidence. The Linux signed-image rehearsal additionally restores the dump into a clean, networkless PostgreSQL container and uses the signed Core image to compare the recovered Knowledge index to the recovered files. The rehearsal uses temporary trust authentication solely inside an isolated, disposable synthetic database.

The operator entry point exposes `capture-recovery-set`, `verify-recovery-receipt` and `restore-recovery-files` through `python -m scripts.vesselctl --help`. Capture requires a previously completed `stop` and `finish-stop`, approved restic binary digest, private staging and password files, a signing key, and a new receipt path. `restore-recovery-files` creates a new directory containing verified Core files and the PostgreSQL custom dump; it does not activate that directory as a vessel installation.

After a stopped signed release switch, capture a new set while that updated release is active. The receipt binds the updated release ID, indexed sources, database dump and Core audit checkpoint. The Linux rehearsal restores this set on a clean second installation after removing the source volume and verifies the updated signed Core image, history and database roles. The earlier pre-update receipt remains a separate recovery point.

`activate-recovery-set` accepts the signed vessel bundle, matching Console configuration, signed recovery receipt, approved restic binary, separate lab credential, and new private installation and Core-state directories. It rejects an unsupported signed Knowledge/Core state compatibility contract before decrypting the recovery set or creating an installation root. It refuses an existing installation ID or data volume. It restores the signed files into private temporary staging, copies only Core state into the new external state directory, initializes a new networkless Knowledge volume with fresh SCRAM administrator and application credentials, restores the PostgreSQL dump, reassigns the five known Knowledge tables to the migration role, grants the ingestion and read roles only their required table privileges, and checks the full index against restored source bytes using the signed Core image. It starts Core and Console, checks health and signed image identity, and records activation only after those checks pass. The dump is never mounted into the running Core state.

This is a clean-host synthetic activation path. The source installation's labelled Docker resources must be absent. The same installation ID is preserved from the signed receipt, while PostgreSQL role passwords are regenerated. A failed candidate removes resources only when its own newly created Knowledge handle is known; ambiguous Docker inventory retains private state for inspection. The current implementation does not perform an in-place replacement or rollback of a live installation.

Activation writes an owner-only restore intent before creating the database volume. If the process stops before activation completes, generic first-install `resume-install`, `reconcile-install` and `reset-bootstrap` commands refuse that root. This prevents a partial PostgreSQL restore from being treated as a fresh document ingestion. Automatic in-place resume of a partial restore remains open.

`abandon-incomplete-restore --discard-partial-data` verifies the signed receipt, restore and first-install intents, signed staged release, absent active record, and complete installation-scoped Docker inventory. Each clean restore also generates a unique 128-bit attempt ID in its private intent and Knowledge data-volume label. The abandon command requires that exact attempt label before deletion, so a later volume with the same installation ID cannot be mistaken for the old candidate. It accepts either the partial data volume alone or one interrupted networkless Knowledge container with its labelled socket and data volumes. Before removal, it verifies the container's installation, role, run name, network mode, port bindings and volume mounts, and checks both volumes' labels. Any network, second container or extra volume refuses cleanup. It removes only the checked container and volumes, proves they are gone, and writes an owner-only abandonment record. Repeating an abandoned command refuses without touching Docker. The restore intent, staged release and Core state remain for inspection; generic first-install commands continue to refuse that root. A retry uses a new private installation and Core-state path with the same signed receipt. It does not automatically discard documents or credential files.

`retry-abandoned-restore` checks the owner-only abandoned record, original restore and first-install intents, signed staged release, receipt, clock, absent old active record, and separation of old and new paths. It then runs the clean activation path with a fresh restore-attempt ID, new private installation root, new Core-state directory and fresh database credentials. The old abandoned evidence remains. A failed retry keeps the original evidence and follows the clean activation cleanup rules for its new candidate. The Linux rehearsal verifies the new signed Core and Console runtime, restricted database, retained conversation history and absence of a dump in running Core state. This is a clean-host retry, not an in-place rollback of an active installation.

The capture is a bounded synthetic candidate: at most 120 approved sources, a 16 MiB PostgreSQL dump, 16 MiB audit trail and 256 MiB conversation database. Production recovery still needs independently reviewed credential custody, role and privilege restoration, target-hardware rehearsal, an operator runbook, and a safe in-place replacement and rollback design. Signing and restic keys remain outside the snapshot and need separate custody. A local repository is not an off-vessel copy.

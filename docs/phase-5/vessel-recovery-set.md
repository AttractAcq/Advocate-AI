# Coordinated synthetic vessel recovery set

The vessel recovery capture requires a stopped, signed installation. It holds the vessel operation lock and the policy directory lock, verifies that only the labelled Knowledge data volume remains, freezes the approved Core sources, policy, audit chain and SQLite history, then starts the signed Knowledge image on that volume without network access. The signed Core image checks the complete document index against the frozen source bytes. A bounded PostgreSQL custom dump and the frozen Core files enter one encrypted restic snapshot. An Ed25519 receipt signs the snapshot ID, release and installation IDs, source and passage counts, audit checkpoint and dump hash.

Restoration first verifies the receipt and encrypted repository, then restores into a new directory. It checks every restored source, policy, audit checkpoint, SQLite integrity and dump hash against the receipt. The Linux signed-image rehearsal additionally restores the dump into a clean, networkless PostgreSQL container and uses the signed Core image to compare the recovered Knowledge index to the recovered files. The rehearsal uses temporary trust authentication solely inside an isolated, disposable synthetic database.

The operator entry point exposes `capture-recovery-set`, `verify-recovery-receipt` and `restore-recovery-files` through `python -m scripts.vesselctl --help`. Capture requires a previously completed `stop` and `finish-stop`, approved restic binary digest, private staging and password files, a signing key, and a new receipt path. `restore-recovery-files` creates a new directory containing verified Core files and the PostgreSQL custom dump; it does not activate that directory as a vessel installation.

`activate-recovery-set` accepts the signed vessel bundle, matching Console configuration, signed recovery receipt, approved restic binary, separate lab credential, and new private installation and Core-state directories. It refuses an existing installation ID or data volume. It restores the signed files into private temporary staging, copies only Core state into the new external state directory, initializes a new networkless Knowledge volume with fresh SCRAM administrator and application credentials, restores the PostgreSQL dump, reassigns the five known Knowledge tables to the migration role, grants the ingestion and read roles only their required table privileges, and checks the full index against restored source bytes using the signed Core image. It starts Core and Console, checks health and signed image identity, and records activation only after those checks pass. The dump is never mounted into the running Core state.

This is a clean-host synthetic activation path. The source installation's labelled Docker resources must be absent. The same installation ID is preserved from the signed receipt, while PostgreSQL role passwords are regenerated. A failed candidate removes resources only when its own newly created Knowledge handle is known; ambiguous Docker inventory retains private state for inspection. The current implementation does not perform an in-place replacement or rollback of a live installation.

The capture is a bounded synthetic candidate: at most 120 approved sources, a 16 MiB PostgreSQL dump, 16 MiB audit trail and 256 MiB conversation database. Production recovery still needs independently reviewed credential custody, role and privilege restoration, target-hardware rehearsal, an operator runbook, and a safe in-place replacement and rollback design. Signing and restic keys remain outside the snapshot and need separate custody. A local repository is not an off-vessel copy.

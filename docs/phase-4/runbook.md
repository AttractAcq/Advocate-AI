# Phase 4 synthetic intelligence runbook

1. From the repository root, run `make check` and `cd apps/console/web && npm run build`.
2. Start the existing local Core and Console per the [Phase 2 runbook](../phase-2/runbook.md). Sign in as `lab-avit_admin-1` using the configured lab passphrase.
3. Open **Security**. The three synthetic incidents come from `fixtures/phase-4/wazuh-alerts.json`; their asset map is `fixtures/phase-4/assets.json`. Inspect the Wazuh alert ID, index document ID, timestamp, asset match, source location, confidence limit and suggested checks. Use both index and document IDs when checking the source alert. The optional time filter accepts a range of at most seven days. Opening an incident also checks up to 100 supported alerts within one hour before and after it, showing at most 20 with the same explicitly resolved source asset and their own source references. An unresolved source produces no device association. This is a bounded sample, not an exhaustive incident correlation or a causal claim.
4. Select **Explain event** only when the loopback model is running. For a known asset, Core sends the primary alert and at most five additional same-source alerts' IDs, timestamps and severities to the model, excluding the related alerts' free-text descriptions. Core displays the cited events supplied to the model. A failed related-alert search falls back to primary-only model context; an unsafe model answer falls back to the primary cited summary. For an unknown or ambiguous asset, Core returns an evidence-only summary without guessing a device. The analyst checks the independent alert source before acting; a shared asset and time window do not establish a common cause.
5. Stop the local model. The incident list and detail should still load; explanation should report unavailable. This exercises API separation only. It does not simulate independent Wazuh collection.

With the local `qwen3.5:2b` model already available through the loopback OpenAI-compatible API, run `.venv/bin/python -m scripts.phase4_context_evaluate` to reproduce the [one-run contextual answer record](contextual-answer-evaluation.json). The script creates only fictional alerts in a temporary directory, uses the AV/IT lab role, and checks the two cited IDs, an out-of-window exclusion, related-text injection exclusion and unknown-source fallback. Review the generated sentence against the cited fixture fields; those automated checks do not prove general claim support or quality.

Run `.venv/bin/python -m scripts.phase4_context_matrix` for the [four-case local model record](contextual-answer-matrix.json). It checks the five-related-alert cap against seven same-source events, a switch with no related alert, an unmapped source, and an instruction-like primary alert. It compares every time stated in the answers with the cited synthetic events. The model once invented a 30-minute interval from event times; Core now asks for exact supplied timestamps and rejects numeric duration claims, falling back to the primary cited summary. This is a local model check, not independent analyst approval or evidence of Wazuh collection.

Optional future lab configuration: set `SOVEREIGN_WAZUH_INDEXER_ENDPOINT` to the private HTTPS indexer URL, `SOVEREIGN_WAZUH_READ_TOKEN` to a separately scoped read token, and `SOVEREIGN_WAZUH_CA_BUNDLE` to an absolute path for the trusted PEM CA bundle. The endpoint and token must be provided together. The CA file must be a regular file owned by the Core process user, have one link, permit no group or other access, and be at most 64 KiB. Core loads its trust into memory during startup; replace the file and restart Core to rotate the CA. The reader calls only `POST /wazuh-alerts*/_search` with at most 100 alerts and an explicit field list; exact lookups query both the index name and document ID. No secret belongs in the repository, command history or test fixtures. Confirm the token's permissions and source network path separately on the actual lab host.

The current switch and host alerts are representative structured Wazuh records. Their vendor-specific collector mappings are not yet implemented or verified. The FortiGate parser accepts a representative key-value syslog line and returns only approved fields. This is a software adapter test, not a claim that a FortiGate or Wazuh appliance generated the event.

02 — Sovereign Core
This is the application brain, but not the language model itself.

It determines what happens when a crew member submits a request.

For example:
1. Receives the question.
2. Authenticates the user and obtains their authorised scope.
3. Determines whether document retrieval or an approved security tool is needed.
4. Calls the relevant service with restricted permissions.
5. Sends the permitted context to the local AI model.
6. Returns the answer, citations and authorised results.
7. Records the relevant audit event.
We must program this orchestration and the internal APIs.

We don't need to build the inference engine. vLLM already exposes a compatible model-serving API. However, its documentation warns that API-key authentication alone does not secure every endpoint, so the inference service must remain behind our protected application boundary. 
GitHub

03 — Knowledge Engine
This is one of the most commercially valuable parts of our software.

We need to build an application that can connect to the yacht's approved documents, understand their structure, create searchable indexes and provide relevant information to the AI model.

Our custom code would handle document import, folder-to-department mapping, access-control metadata, incremental indexing, deletion and permission-change propagation, source references, and retrieval quality.

For instance, we would develop an adapter that reads approved QNAP folders, maps their permissions and processes supported files through Docling.

This produces a secure vessel-specific knowledge base without needing to retrain the language model on each yacht's documents.
04 — Policy Engine
This is the part I would give the greatest engineering scrutiny.

Keycloak already supports fine-grained authorisation policies, including role-based and attribute-based controls. 
Keycloak


Our proprietary work is to translate a yacht's organisational and document structure into enforceable policy.

For example:
User	Permitted information
Captain	Approved command and management documents
Chief Engineer	Engineering and technical records
Chief Stewardess	Approved interior and hospitality records
Deckhand	General operational SOPs and permitted deck records
AV/IT administrator	Technical system records, without automatic access to private owner documents

These are default policy examples, not universal access rights. Each vessel's owner or management must approve its access model.

The policy engine must reject unauthorised retrieval before confidential content reaches the AI model. It must also control file downloads, search results, citations, cached content and tool use.

This requires specialist security review. OWASP identifies prompt injection, sensitive-information disclosure and weaknesses in vector retrieval systems as important AI application threats. 
OWASP Gen AI Security Project

05 — Intelligence Engine
This is the component that turns a private AI assistant into a cybersecurity and operational intelligence product.

Instead of writing our own intrusion-detection software, we use Wazuh and other security technologies to generate reliable events.

We develop:
- Connectors to read approved security events.
- Normalisation logic to translate events from different hardware manufacturers.
- AI-assisted analysis and correlation of findings.
- Vessel-specific asset and network context.
- Incident summaries with supporting evidence.
- Read-only investigation tools and reports.
For example, a FortiGate event might identify a device making repeated suspicious connections. Sovereign would associate the IP address with a known device, retrieve the relevant event history and explain why an AV/IT officer should investigate it.

Wazuh already provides a server API and offline deployment capability, so we would integrate it rather than recreate its SIEM functionality. 
Wazuh server API · Wazuh documentation+1

06 — Vessel Connect & Deploy
This module makes the product repeatable.

We would develop adapters for supported NAS systems, firewalls, switches, monitoring systems and onboard infrastructure.

We would also build the installer, offline update manager, configuration validator, backup integration, rollback process and diagnostics.

This is what prevents us from having to manually build the software from scratch for every client.

For example, the first QNAP integration should become a reusable adapter. When a second yacht also has QNAP storage, we configure that existing adapter rather than write a new integration.
07 — Sovereign Fleet
This is the company's management application, not something every yacht needs to connect to.

It would maintain customer records, supported hardware configurations, software versions, signed release packages, licence entitlements, maintenance schedules, support tickets and engineer assignments.

For the strict zero-egress product, it would not collect vessel documents, prompts, embeddings or security logs. Deployment and health records would only be imported through expressly authorised offline or administrative procedures.

02   Indicative engineering sequence
The planning sequence below assumes a small multidisciplinary team and overlapping work. Week ranges are directional, not commitments. Discovery, hardware sourcing, classification review and security remediation can extend the programme.




PHASE 0  |  Technical definition and security baseline


Gate to exit: G0 — signed technical baseline and test plan.
T-001  Define the V1 operating model
Confirm Strict Sovereign Mode: no AI requests, documents, embeddings or security telemetry leave the vessel by default.
Define allowed users and workflows: approved document Q&A, cited summaries, draft reports, read-only security analysis.
Define exclusions: no autonomous network changes, no safety-critical interfaces, no uncontrolled internet access.
Output / evidence: Scope statement, feature boundaries, deployment-mode decision.   |   Lead: Product/technical lead
